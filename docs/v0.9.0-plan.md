# Sailune v0.9.0 implementation plan

Status: implemented for v0.9.0; release verification is recorded in the project verification/release notes.

This is the canonical cross-project plan for Sailune CLI/shared Go core,
Sailune Desktop, and Sailune Mobile. All three projects target **v0.9.0**, moving
forward from v0.1.0 together. This is a substantial product milestone, not a claim
that the project has reached semantic-versioning 1.0 stability.

The release introduces personal collections and two independent artwork slots
per story while preserving Sailune's minimal reading-room interface. This
document records product behavior, engineering scope, and release acceptance
criteria. Proposed technical defaults below are implementation targets; tune
them through measured device and visual testing without changing the agreed
product behavior.

## 1. Architecture and ownership

- The public Go library in `sailune-cli` remains the authority for persistent
  library data, validation, collection matching, image assets, and transfers.
- Desktop calls the embedded library through its Wails adapter. Mobile calls it
  through the existing Go/Android bridge. Neither client invokes the CLI binary.
- Flutter and Svelte own layout, image previews, settings, and interaction.
  Native adapters own file selection and platform-specific file access.
- Artwork appearance settings are device-local preferences, like theme settings.
  They are not stored as story metadata or transferred as library data.
- Collections and artwork are personal data. Refreshing website metadata must
  preserve them. Smart collection results can change when refreshed tags change.
- Ship useful terminal commands over the same core APIs; CLI command work does
  not need to precede client implementation.
- Mobile scope is the existing Android Flutter application. iOS is not included.

## 2. Collections

### 2.1 Data and behavior

Collections are independent of reading status and personal tags. A story can be
Reading, belong to `trauma-inducing`, and also belong to `favorites`.

Support two collection types:

1. **Manual:** membership changes only through an explicit user action.
2. **Smart:** membership is the result of saved rules evaluated against current
   local library data. No background scraping is triggered by opening one.

Manual collection operations:

- Create, rename, and delete a collection, including an empty collection.
- Add or remove one or multiple stories.
- Put a story in multiple collections without duplicating the bookmark.
- Filter the library by collection and show a full-library story count.
- Deleting a collection removes its membership records, not the stories.
- Deleting a story removes its collection memberships.
- Repeating an add/remove operation is safe and does not create duplicates.

Use stable collection identifiers independent of names. Names must be nonempty
after trimming; prevent ambiguous duplicate names using a consistent core-owned
case-insensitive comparison. Renaming must not affect membership or identity.
Do not silently merge different collections solely because their names match.

### 2.2 Tag assistance and smart rules

Provide a tag-assisted action for manual collections: find matching stories,
preview results, select stories, and add them. This is a one-time operation;
future metadata changes do not alter the selected membership.

Smart collections support:

- Personal-tag and effective website-tag conditions, clearly distinguished.
- Match **any** or **all** tags within a condition.
- Optional site, fandom, and reading-status constraints.
- AND between populated condition groups; empty groups impose no constraint.
- Exact normalized tag matching using the shared core's established Unicode
  case-insensitive semantics. Do not infer synonyms or emotional meaning.
- Preview of matching stories before saving, including pagination and count.
- Tag discovery/autocomplete from the entire library, not just its visible page.
- A visible automatic-collection indicator and an explanation that edits or
  successful source refreshes may change membership.

Use effective website metadata so existing local metadata overrides are honored.
FFN currently supplies genre-derived tags while AO3 supplies richer tags; do not
promise equal coverage or semantic equivalence between sites.

For v0.9.0, keep manual and smart membership separate. Manual exceptions inside
smart collections, arbitrary nested boolean rules, semantic similarity, and AI
classification are outside scope. A rule result can instead be used to populate
a manual collection when users want fixed, subjective curation.

### 2.3 Collection interface

- Keep the library as the main destination.
- Add an `All collections` selector that filters the existing library; combine
  the selected collection with current search, status, and other filters.
- Put `Manage collections` in that selector.
- Provide a dedicated management page listing collections, type, and counts,
  with create, rename, and delete actions. On desktop an equivalently spacious
  dialog is acceptable if keyboard navigation and available space remain good.
- Open collection details to manage manual membership or edit smart rules.
- Add an `Add to collection` action to story details and a bulk-selection flow
  in library/collection management. Ordinary assignment must not require a trip
  through the management page.
- No permanent sidebar or new primary navigation destination is required.
- Make destructive collection actions explicitly say that stories are retained.

## 3. Two independent artwork slots

Each story has an optional **portrait cover** and an optional **horizontal
background**. Users may set either, both, or neither. Never require users to
stretch a portrait image into a banner or synthesize one role from the other.

- Portrait display frame: 2:3.
- Background: wide landscape artwork, cropped to fit each display surface.
- Provide preview, replace, and remove for each slot independently.
- Provide crop/framing controls and a background focal point. Persist framing
  information needed to reproduce the user's selection on another device.
- A wide source can still crop differently in a library card and detail header;
  preview these uses rather than promise identical framing.
- Custom artwork is displayed without the existing decorative site watermark.
  Site identity remains available in story details/accessibility text.
- Default artwork and logos are bundled with the clients. No per-story image
  record is needed for a missing slot.

### 3.1 Library appearance setting

Label the device-local setting **Library cover appearance**:

| Mode | Image and layout | Missing-image fallback |
| --- | --- | --- |
| Portrait | 2:3 cover on the left, title/author alongside, chapter controls below across the card | Neutral grey portrait cover with site icon |
| Background | Horizontal artwork fills the card behind a theme-aware translucent surface | Existing plain card with translucent site-logo cutout at bottom right |
| Hidden | Neither stored image is rendered | Existing plain card with translucent site-logo cutout at bottom right |

Hide the separate card watermark in portrait mode. In background mode, show the
existing watermark only for the missing-background fallback. Never double up
the default artwork's logo with another decorative logo.

Preserve Hidden as the initial setting for upgraded installations. Use Hidden
as the conservative first-run default as well; users can select either art mode
in settings. Switching appearance does not modify, delete, or duplicate assets.

Portrait layout targets a roughly 64–80 logical-pixel-wide image on mobile,
subject to visual testing. Keep room for titles and status folds. Adapt the layout
at large text sizes rather than clipping controls or making titles unusable.

Background mode aims for a restrained glass appearance:

- Artwork beneath a theme-aware translucent surface and subtle edge highlight.
- Text, buttons, status, and progress controls remain fully opaque and readable.
- Modest blur only where performance permits; cache or prepare repeated effects.
- Verify dark, bright, high-detail, and text-heavy artwork in both themes.
- Respect platform accessibility preferences and provide an opaque/reduced-effect
  fallback where needed.

Advanced optical refraction/distortion is not a v0.9.0 requirement. Prototype
the glass treatment before committing to expensive live effects on scrolling
cards. Any extra prepared variants should be regenerable cache data.

### 3.2 Story-detail composition

Use the Steam-inspired composition agreed for both clients:

1. A horizontal artwork header begins the story-detail page.
2. Its lower edge gradually fades into the actual page background color.
3. The centered 2:3 portrait overlaps the transition between header and page.
4. Title, author, reading actions, summary, and remaining details begin below
   the portrait. They are not drawn over the artwork.

```text
┌────────────────────────────────────┐
│  Back                       Edit   │
│                                    │
│         Horizontal artwork         │
│                                    │
│             ┌──────────┐           │
│ · · gradual │          │ fade · ·  │
│             │ Portrait │           │
│             │  cover   │           │
│             │          │           │
│             └──────────┘           │
│                                    │
│             Story title            │
│              by Author             │
│       Progress / reading actions   │
│                                    │
│  Summary and other story details   │
└────────────────────────────────────┘
```

- Missing background: neutral theme-appropriate header with the site-logo cutout
  near its bottom-right, fading into the page.
- Missing portrait: neutral grey 2:3 cover with site icon.
- Use the appropriate fallback independently when only one asset is present.
- Portrait receives a subtle border/shadow to separate it from the header.
- Back/edit controls receive a reliably readable surface.
- Begin with a portrait width around 140–180 logical pixels on mobile; tune
  header height so title and reading actions are not unnecessarily pushed down.
- Desktop retains this centered overlapping composition in its detail surface;
  it does not switch to the earlier side-by-side cover/title proposal.
- Allow a larger artwork preview from the detail view.

The library's three-way setting does not change this detail composition. Provide
a separate device-local **Show artwork in story details** toggle, initially on.
When off, render a compact plain detail header with no reserved artwork gap.
Users can hide artwork throughout by selecting Hidden and disabling this toggle.

## 4. Image processing and storage

### 4.1 Managed assets

Store normalized compressed image bytes in a separate SQLite BLOB asset table,
not in bookmark JSON. Associate stories with assets by role (`cover` or
`background`) through an association table, with per-association framing data.
Use content-derived asset identifiers/checksums to support deduplication and
validation. The core owns asset lifecycle and reference cleanup.

- Save a managed optimized copy; never persist only an original desktop path or
  Android document URI. Never modify the user's original file.
- Do not retain camera-sized originals by default.
- Keep format, dimensions, byte length, and checksum with the asset.
- Store generated thumbnails separately from ordinary bookmark payloads.
- List/get story responses carry asset references and presentation metadata,
  not full image bytes. Load images separately and cache them in clients.
- Changing an asset must invalidate the relevant cached display.
- Replace/remove associations transactionally. Delete assets only when no
  remaining story/role references them.
- Default art consumes no per-story database image space.

### 4.2 Automatic optimization

Optimization is automatic, not a task users have to remember or an advanced
settings requirement. Show a short notice: `Sailune saves an optimized copy.`

Processing order:

1. Bound input bytes and inspect dimensions before allocating a full decode.
2. Validate actual format; enforce limits on decoded dimensions/pixel count.
3. Apply orientation and selected crop/framing.
4. Downscale without enlarging small sources.
5. Re-encode to an explicitly supported static format, stripping unnecessary
   metadata, including photo location.
6. Generate thumbnail/display variants and save the asset and association.

Initial tuning targets:

| Property | Portrait | Background |
| --- | --- | --- |
| Selected input limits | 25 MB and 40 megapixels | 25 MB and 40 megapixels |
| Saved dimensions | Fit within 1,000 × 1,500 px | Long edge at most 2,000 px; preserve selected landscape framing |
| Encoding starting point | JPEG quality around 80–85 | JPEG quality around 80–85 |
| Encoded asset ceiling | 750 KB | 1 MB |
| Small display variant | Fit within 160 × 240 px | Derive from measured card needs |

The background targets extend the earlier portrait-only proposal and should be
validated during implementation. Reduce quality within a reasonable range, then
dimensions to meet the ceiling. Define transparency handling explicitly, using
a supported format or a deliberate flattening preview. Do not silently produce
black or otherwise surprising backgrounds.

Initially support ordinary JPEG/PNG input. Native conversion may support other
common picker formats, but the core must validate the converted result too.
Camera RAW and animated artwork are outside scope; explain unsupported formats
clearly. Imports must receive equivalent validation. Do not repeatedly re-encode
already-valid optimized backup assets and degrade quality on every round trip.

Bound work and memory as well as output size. Avoid passing large images as
base64 inside existing JSON calls; extend native/core file or byte interfaces as
needed, with work off the UI thread and safe temporary-file cleanup.

## 5. SQLite migration and portable backups

### 5.1 Database evolution

The current store accepts SQLite schema version 1 only. Add a transactional,
versioned migration path for collections, rules, associations, and image assets.
Application version, SQLite schema version, and backup format version are
independent; do not set all three to 0.9.0 mechanically.

- Preserve all existing stories, IDs, ID watermarks, metadata, overrides, notes,
  ratings, progress, timestamps, and personal tags.
- Add indexed collection membership and role/asset references with foreign keys.
- Evaluate collection filters/counts in SQLite before pagination. Do not filter
  a loaded client page or decode the full library to compute a shelf.
- Make migrations recoverable on failure and refuse unknown future schemas.
- Older binaries will not understand a migrated schema. Coordinate the bundled
  desktop CLI and embedded core upgrade, and explain rollback requires a
  compatible pre-upgrade backup rather than an older binary opening new data.
- Keep pre-upgrade recovery data safe and avoid unexpected database overwrites.

### 5.2 New archive format

Export one user-selected ZIP backup containing:

```text
sailune-backup.zip
├── manifest.json       # Format/version, asset metadata/checksums
├── library.json        # Stories, collections, rules, memberships, art references
└── assets/             # Each referenced optimized image once
    ├── <asset-id>.jpg
    └── <asset-id>.png
```

- Include both artwork roles and framing metadata.
- Regenerate thumbnails/caches on import; do not require them in the archive.
- Export from a consistent database read snapshot so records and images agree.
- Stream the archive to a file/output handle instead of building it in a string.
- Continue importing existing version-1 JSON backups.
- If retaining legacy JSON export, label it explicitly as excluding v0.9.0
  collections/artwork; it is not a complete backup and must not be the default.
- Reject unsupported future formats with a clear error rather than discard data.
- Do not export authentication sessions or device-local appearance preferences.

Mobile currently limits backup files to 16 MiB and transports snapshots through
strings. Replace that path with bounded file-based streaming through the native
document picker. Merely increasing the string limit is not the solution. Select
and document per-asset, entry-count, total-expanded-size, and archive-size limits
after device testing; enforce them while reading, not after extracting everything.

Validate archive paths, duplicate entries, checksums, actual image formats,
dimensions, references, and format versions. Prevent path traversal and excessive
decompression. Stage/validate before committing; failed imports must preserve the
existing library and clean up temporary resources.

### 5.3 Restore and merge policy

- **Restore:** requires a pristine destination and restores the complete library,
  collections, images, and associations, preserving applicable IDs/watermarks.
- **Merge stories:** match canonical URL and map every incoming story ID to its
  destination ID, including stories already present. Preserve existing personal
  story fields, following the current non-overwriting merge principle.
- **Merge art:** independently per role, fill a missing destination image from
  the incoming story; keep an existing image and its framing by default. Import
  only assets needed for resulting associations.
- **Merge manual collections:** identify by stable collection ID, union mapped
  memberships, and preserve destination collection metadata on conflict.
- **Merge smart collections:** preserve destination rules for an existing stable
  ID; report conflicts rather than silently replace rules.
- Different collection IDs with the same name stay distinct using a predictable
  imported-name suffix. Re-importing the same archive must not create new copies.
- Show an import summary covering added/skipped stories, collections, filled art
  slots, and retained conflicts. State that existing art/rules take precedence.
- Restore/merge writes should commit atomically, including asset associations.

These are backup/transfer features, not synchronization. Merge does not reconcile
deletions or subsequent edits bidirectionally. Live SQLite cloud synchronization
and cross-device conflict-resolution services remain outside scope.

## 6. Changes by repository

### 6.1 `sailune-cli`: shared core and terminal interface

Primary areas: `internal/model`, `internal/library`, `internal/cli`, `sailune.go`,
`docs/storage.md`, public API tests, and transfer/migration tests.

- Add public collection, rule, artwork, and transfer types/APIs.
- Add schema migration, indexed membership/rule queries, counts, tag discovery,
  image processing/storage, and full archive import/export.
- Preserve source-refresh concurrency guarantees for all new personal data.
- Add thin terminal commands for collection create/list/show/rename/delete,
  manual add/remove, rule create/edit/preview, and collection-filtered story lists.
- Add artwork set/remove/info/file-export operations with an explicit role.
  CLI does not render glass/cards; it manages the same data as the clients.
- Expose framing through validated arguments where needed; graphical crop tools
  remain client responsibilities.
- Make full archive export the normal backup path and retain legacy import.
- Document defaults, limits, merge rules, compatibility, and terminal examples.

Exact command spelling should follow the existing CLI conventions during
implementation; the behaviors above are required regardless of spelling.

### 6.2 `sailune-desktop`

Primary areas: `internal/desktop/service.go`, `app.go`, `frontend/src/api.ts`,
`App.svelte`, `Story.svelte`, `Editor.svelte`, `Settings.svelte`, `style.css`, and
frontend/adapter tests.

- Extend typed requests/responses and Wails bridge actions for the new core APIs.
- Add native image selection, preview/framing, and separate asset retrieval.
- Add collection management, selection/filtering, bulk assignment, tag discovery,
  and smart-rule editing/preview.
- Add both art slots to editing, three library appearances, device-local settings,
  and the centered overlapping detail composition.
- Provide bounded image delivery/caching without arbitrary filesystem exposure
  or full image data in every JSON story response.
- Update backup dialogs to use archive files while accepting legacy JSON imports.
- Preserve keyboard focus, Escape behavior, reduced motion, readable contrast,
  and existing progress interactions in every appearance.
- Update the pinned core and build/package the companion CLI from the same core
  revision; update release/version metadata to v0.9.0.

### 6.3 `sailune-mobile`

Primary areas: `core/mobile`, `lib/data/library.dart`, `lib/models/story.dart`,
`lib/widgets/story_card.dart`, library/story/editor/settings screens,
`MainActivity.kt`, and channel/widget/integration tests.

- Extend the gomobile facade, Kotlin channel, Dart interface, and fake library
  support for collection and artwork APIs.
- Use native document/photo selection with access limited to selected files.
- Add crop/focal-point previews, bounded background processing, image retrieval,
  caching, cancellation/error handling, and temporary-file cleanup.
- Replace string-based backup transfer with file-based streaming.
- Add collection pages, selector, bulk assignment, rule editor, and full-library

- Add two independent art editors, the three library modes, local preferences,
  and the centered overlapping detail composition.
- Preserve large-text layout, touch targets, back navigation, pull-to-refresh,
  progress controls, and reduced motion.
- Update core dependency pins, rebuild Android bindings, and update app/release

## 7. Delivery sequence

1. Confirm visual layouts using synthetic examples: all modes, both themes,
   each missing-art combination, long titles, and large text. Prototype glass
   performance on Android and the desktop webview.
2. Implement versioned core migrations and manual collections, with terminal
   operations and transfer tests.
3. Integrate manual collection management and assignment in both clients.
4. Implement tag discovery, tag-assisted assignment, and explicit smart rules;
   integrate preview/count/filter behavior in both clients.
5. Implement two-role asset storage, bounded optimization, archive transfers,
   and merge handling; add terminal asset operations.
6. Integrate native image selection, streaming transfers, appearance settings,
   card modes, and story-detail artwork in both clients.
7. Complete migration, transfer, accessibility, visual, performance, and platform
   verification; align all three versions and publish coordinated release notes.

Development steps may overlap, but do not ship artwork without a complete backup
path or upgrade a shared desktop database while bundling an incompatible CLI.

## 8. Acceptance criteria

- Existing v0.1.0 libraries upgrade with personal data and progress preserved.
- Manual memberships survive rename, source refresh, export, restore, and merge.
- Deleting collections never deletes stories; deleting stories cleans references.
- Smart results/counts remain correct across pagination and metadata overrides;
  Unicode tag matching and ANY/ALL/group-AND behavior are covered.
- A story with neither, either, or both artworks renders correctly in all modes.
- Hidden settings retain stored assets; default artwork adds no database assets.
- Custom art has no duplicate watermark; missing-art fallbacks match the plan.
- Header fade works in both themes, overlap does not obscure text, and large
  accessibility text/touch/keyboard interactions remain usable.
- Huge dimensions, oversized inputs, corrupt files, unsupported formats, and
  malformed archives fail safely with actionable messages.
- Optimization corrects orientation, strips location metadata, respects limits,
  and leaves originals untouched. Backup round trips do not degrade image quality.
- Full backups restore both roles, framing, collections, and all existing fields.
- Merge maps memberships onto existing stories, fills only missing art slots,
  handles collection conflicts predictably, and is repeatable without duplicates.
- Interrupted/failed writes and imports do not leave broken references or partial
  library changes. Concurrent CLI/desktop operations preserve consistency.
- Test archives larger than the old mobile 16 MiB limit without whole-backup
  strings or excessive memory growth; measure limits on representative devices.
- Scrolling does not decode original-size images per card or repeatedly execute
  expensive uncached blur; measure memory/frame behavior with a large art library.
- Verify Go core/public/CLI tests, native adapters, Flutter analysis and relevant
  widget/golden/integration tests, Svelte/TypeScript checks, desktop browser tests,
  and production builds. Record native platform checks separately from simulated
  tests and document any unverified platforms before release.

## 9. Effort and exclusions

Planning estimate: approximately **7–11 developer-weeks** for one developer
familiar with all three repositories, including two artwork roles, collections,
simple glass styling, transfer migration, client integration, and verification.
This consolidates and expands the earlier feature estimates; it is not a delivery
date or a claim based on an implementation prototype. Image/native bridge work
and cross-platform visual verification carry the most uncertainty.

Excluded: iOS, automatic cross-device sync, semantic/AI grouping, nested
collections, manual exceptions to smart membership, camera RAW/animated art,
original-photo archival, advanced optical liquid-glass simulation, website art
scraping, and automatic artwork generation. No external accounts or services are
required for the planned features.
